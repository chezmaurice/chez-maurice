# Households, rooms & devices

This is the social layer — the part that makes Maurice a *household* assistant rather than a single-user chatbot. Several of the [[maurice|differentiators]] live here: free user-switching on a shared device, multi-person rooms, and being a guest across households.

The shape in one line: **a server is one household; a device can hold several households; switching member is a tap and a PIN.**

## Onboarding & pairing

First run is `app/Maurice/Views/PairingView.swift`: you enter a server URL, the app calls `GET /api/health` to confirm it and read the household's identity (name, colour, icon), and stores it as a local **Household** (`Services/SessionStore.swift`, persisted to UserDefaults). Pairing is device-local, and a device can pair **multiple** households.

Then `UserPickerView.swift` is the member grid, with three ways in:

- **PIN** — tap your avatar, enter your PIN → `POST /api/auth/login` (`{ user_id, pin }`).
- **Admin** — username + password → `POST /api/auth/login`. Changed in Settings → *Administrator password* (`POST /api/auth/password`, 31 October 2026): the current one, then a new one of at least 12 characters that does not contain the username; the admin's other devices are signed out.
- **Invite code** — `POST /api/auth/enroll` redeems a code; if you're a standard member you then set a PIN (`/api/auth/set-pin`). Guests enroll without one. The PINs everybody tries first (1111, 1234, 2580, 1212…) are refused, by the app in the member's language and by the server (`services/credentials.ts`).

**On the device** (21 October 2026). The session tokens and the member's `maur_` web-link token live in the **Keychain** (`TokenVault` in `SessionStore.swift`; Carnet's in its App Group's access group, so its share extension reads them too), no longer in plain UserDefaults; each app moves what it finds there once, at launch, and erases the plain copy only when the Keychain holds it. Sessions never expire, so a **401** to any request that carried a token means the session was revoked or the member removed: the app forgets that token (and the web-link token with it) and, for the member on screen, goes back to the member picker, which says the session ended. A member **without a PIN** and without a session on the device cannot be signed in by a tap — the server never opens one on a member's id alone — so the tap offers the invite code instead. After every sign-in the app reads the member's own row (`GET /api/users/me`): the household list gives no `username` to a non-admin, and *My data*'s erase confirmation asks for it.

Invite codes (`server/src/services/auth.ts`) are 8 characters from an unambiguous alphabet (no I/O/0/1), one active per member, valid ~7 days, reusable within the window; `/api/auth/enroll` is the public guessing surface so failed attempts are rate-limited per-IP and globally. Every such code is the admin's, so a code that brings a device into an account **already in use** (a PIN set, or a session open) is told to its member: see below. Sessions are opaque 64-char tokens, refreshed on use.

**Inviting someone, by QR code (25 September 2026).** Besides a member's own code (a new device for someone already here), an admin can invite *someone* — no member exists until the code is used (`household_invites`, `server/src/services/invites.ts`). It is **single use**, valid seven days: the first `enroll` call without a name answers `needs_profile` and leaves the code unused, the app asks "who's joining?" (first name, colour), and the second call makes a **standard member** — the handle is the name folded to ASCII, numbered when taken — and signs them in; a PIN follows as for any member. The code is claimed in one statement before the member is created, so two phones scanning the same QR code can't both come in. Both kinds are handed out **from the app**: Settings → Members (admins only) shows "Invite someone", the invitations still waiting, and each member's "New device" code, as a QR code with the typed code and a link to send (`/api/users/invites`, `/api/users/:id/invite`). The QR code carries `https://<household>/join?code=…`, **one link for both apps**: an invitation names a household, never an app (2 November 2026).

**A member invites a friend as a guest (3 November 2026).** Any member but a guest — a child only once the admin ticks *May invite friends* (`users.may_invite_guests`, beside *may publish* on the console's member page) — can invite someone **as their guest**: Settings → *Invite a friend as a guest* in the Maurice app, the same in Carnet's member sheet. Same QR code, code and link as an open invitation, single use, seven days, but the `household_invites` row carries `role = 'guest'` and `contact_of = <inviter>`: redeeming it makes a guest whose one contact is the inviter, without a PIN, and `enroll` answers `role: "guest"` and `invited_by`. The friend sees only the inviter in the roster, and talks to Maurice in this household on its budget through the personas open to guests (the invite sheet says so). Routes: `POST /api/me/guest-invite`, `GET /api/me/guest-invites` (with `allowed`), `GET`/`DELETE /api/me/guest-invites/:code`; refused to a guest, to a child not allowed, and to an API token. These invitations stay out of the admin's list; the console shows such a guest as *invité par @…*. Guests do not count as members. It exists for one thing first: being given an entry from the friend's own household ([[maurice-carnet]]).

- **Tapped with an app installed, the link opens it.** Each household serves `/.well-known/apple-app-site-association` (Maurice first, then Carnet: iOS opens the first one installed) and `/.well-known/assetlinks.json` (both Android apps, release key only), from `services/appLinks.ts`. The apps declare `*.chezmaurice.eu`. For that wildcard, Android checks the file on `chezmaurice.eu` itself, which the site serves without its redirect to `www` (`ops/static-site.sh`).
- **Without an app, or on a household under another name** (self-hosted), the link opens the page. It offers **both apps** with the install links of the device it is read on: TestFlight on iPhone, iPad and Mac, Obtainium then the latest release on Android. The links can be overridden with `MAURICE_INSTALL_URL`, `CARNET_INSTALL_URL`, `MAURICE_INSTALL_ANDROID_URL` and `CARNET_INSTALL_ANDROID_URL`. The page sits on Maurice's tile (`/join/maurice-tile.svg`) under one card, like the apps' entry screens. Then come "Open in Maurice" and "Open in Carnet" (`maurice://join?server=…&code=…`, `carnet://join?…`), and the code to type.
- The page doesn't say whether a code is valid, which would make it an unthrottled oracle.

In the apps, the welcome screen's main action is **Scan an invitation** on a phone and **Paste the invitation link** on a computer (Mac, Windows, Linux). **Enter a code or an address** takes a link, an address or a bare code, and asks for the household address when it only has a code.

**Adding one of your own devices (31 October 2026).** A member signed in on one device brings another in without the admin: Settings → *Add a device* (any member but a guest) shows a QR code, the code, the time it has left and a link to send (`POST /api/me/device-code`). The code lives in `device_link_codes`: **single use, ten minutes**, a new one withdrawing the member's unused one, claimed in one statement by `/api/auth/enroll` (checked after open invitations, before the admin's codes). The new device is signed in with no PIN to set (the member has one) and no account event (they made it themselves). The sheet showing the code asks every two seconds where it stands (`GET /api/me/device-code/:code` → pending, used or expired): it says the device is in and closes, or says the code has lapsed instead of leaving a dead QR on screen. A connected tool's `maur_` token cannot ask for one: it would turn a read token into a full session elsewhere. A forgotten PIN still needs the admin's code.

**Leaving, three ways (2 November 2026).** The apps no longer use one word, "Disconnect", for two different things:

- **Switch member** goes back to "Who's here?" and forgets nothing.
- **Sign out** ends this member's session, on the server too (`POST /api/auth/logout`), and drops the token from the device. The household stays paired.
- **Forget this household** removes it from the device, with every member's token, after a confirmation that says so.

In the Maurice app, sign-in steps are system sheets: PIN, invite code, "Who's joining?", the PIN to set, and the admin's password. Every way in that is not "pick yourself" sits under **Other options**: an invite code, *Sign in as admin*, *Forget this household*. The welcome screen shows the app's emblem and name, with "Chez Maurice" beneath. The welcome screen and "Who's here?" sit on the app icon's background, repeated as a 320-point tile from the top-left corner (darkened in dark mode for Maurice), with everything — *Other options* included — on one centred card (at most 420 points wide); the sheets and the scanner keep the system look. The same rule holds on Android and the desktop, and Carnet uses its own dark tile. Carnet follows the same steps and words (the glossary of 2 November 2026, shared keys in `Localizable.strings`).

**On Android and the desktop** (Maurice 0.5.5, Carnet 0.1.5, 2 November 2026) the two apps share these screens (`maurice-android`, `onboarding/`), in Material 3: the steps are bottom sheets and dialogs, the menus *Other options*. The scanner (CameraX and ZXing, no Google service) says what the camera is for before the system asks for it, then shows a frame, *Aim at the invitation's QR code* and *Close*; the desktop has no scanner and pastes the link. Both apps declare the App Link for `https://*.chezmaurice.eu/join` and the `maurice://join` and `carnet://join` links of the page; a link that arrives, even with the app already open, pairs the household and hands the code to "Who's here?". *Sign out* and a revoked session also erase what Carnet keeps on the device for that member (shelf, places, unsent captures, articles' text). Carnet shows the connection notice as Maurice does. *Gap:* the *Add a device* dialog shows when the code lapses, not a countdown, and *Forget this household* does not yet count Carnet's unsent captures.

**The admin's reach, said and told (27 October 2026).** A Maurice belongs to whoever opens it: the admin manages the accounts and can, if need be, get into a member's — the owner's rule, said on the site rather than hidden. Two things reach into an account, and each is told to the member. A device that came in by the admin's code into an account in use (`device_by_code`), and the whole household exported (`household_export`, one line per member). Both are rows of `account_events` (`server/src/services/accountEvents.ts`), written before the session is handed out or the archive made. The app shows them once in an alert when it opens or comes back (*Your household's admin reached into your account*), and then under Settings → My data, *What the admin did in your account* (`GET /api/me/events`, `POST /api/me/events/seen`). A push follows within the minute when one can be sent (`services/accountEventsPush.ts`; never for a row older than a day). The member's first device comes in the same way and is not told: there is nothing of theirs in the account yet.

## Members, roles & guests

Three roles (`server/src/services/users.ts`): **admin** (manages members and household identity), **standard** (full member, PIN-protected), and **guest** (full capabilities but a *limited reach*). Orthogonal to the role, a member can be marked a **child** (`users.is_child`, a box on the console's member page, 19 September 2026): Maurice never opens a conversation on his own for a child, and the night proposes nothing to them — a flag the admin sets, not an age the server knows. A child publishes to the household's public pages only once the admin ticks *This child may publish* on the same page (`users.may_publish`, 26 October 2026); every other member always may. A guest's reach is an explicit allow-list — `guest_contacts`, checked **both directions** by `guestCanReach()` — so a guest sees only themselves plus their contacts in the roster, and can only share rooms with them. Guests get curated [[maurice-personas-hats|Maurices]] through each persona's own access list. This is how you safely **host a guest, or be a guest** in another household.

## Foyer switching (multiple households)

`SessionStore` holds an array of paired households, each with its **own per-household session token** (`maurice.token.<household>.<user>`); `switchHousehold()` flips the active one, and `refreshFoyers()` polls each household's `/api/health` and unread count for the switcher badges. The picker shows a pill per household with a "+" to pair another server. So the same device is your own household *and* the one where you're a guest — and a notification can route a tap to the right one via its `household_tag`.

Each household's face in that switcher is its own: `households.name`, `icon` (an SF Symbol name) and `color` (`#rrggbb`), served by `/api/health`. The admin sets them through `PATCH /api/admin/settings` (`server/src/routes/admin.ts`), which refuses a malformed icon or colour rather than storing it and clears on an empty value; the app falls back to an icon and colour derived from the household's id when they are unset. A hosted household gets all three at sign-up: the tower asks the owner to *describe* their household ("Famille Magi-Kemmler", "Aline Mercier") — that text becomes the name — suggests short addresses from it, lets them pick an icon and colour, and sends the three to the new household. Before 28 September 2026 every household was called "Home".

## Rooms (multi-person conversations)

A conversation is a **room**; a 1:1 chat is just a room with one human. Membership is `conversation_participants`, and access is participant-based — `listConversations()` joins on membership, so you only see rooms you're in. `addParticipant()` enforces guest reach, fans the event to the room, and notifies the newcomer.

Maurice's role shifts with the room: in a 1:1 every message summons him; in a multi-human room he answers **only when mentioned** — `mentionsMaurice()` matches `@claude` / `@maurice` (the ➤ button posts a summon, 💬 posts a human-only message). The composer follows that: in a room 💬 is the **default button** — last in the row, at the far right, filled with the member's accent; ➤ sits to its left and keeps ⌘Return. A 1:1 has no 💬 at all. **Return always breaks the line**, on every device — the on-screen keyboard's, a hardware keyboard's on iPad and the Mac, with or without Shift — so a formatted, multi-line message can be typed: a message leaves only by its button, or by ⌘Return for ➤. Read state (`last_read_at` per participant) drives the per-foyer unread roll-up, which counts rooms where someone else wrote since you last read — and, since 19 September 2026, the conversations [[maurice-chat|Maurice opened on his own]] that you have not opened yet (his replies in a thread you started never count).

Liveness uses two WebSocket channels off `roomBus` (`server/src/services/roomBus.ts`): a per-room channel for live messages, and a **per-user channel** (`/api/me/ws`) for activity — "someone is chatting with you" — even when you're not in that room. Its events: `activity` (a message in a room you are in), `conversation_added` (someone added you), and `conversation_opened` (Maurice opened a conversation for you, with his first message). See [[maurice-server]].

The household guards how often Maurice may open one: "Days between two conversations Maurice opens" in the console's settings (`households.maurice_opens_min_days`, fifteen by default), never for a child, never for a guest; the operator's route (`POST /api/admin/conversations/open`) can pass `force` to step over it, the night never will.

## Moderation

In a shared room, the long-press menu on a message offers **Report** and **Block**. A report carries the message and its metadata to the operator (`/api/reports`, child-safety reports first, then newest); blocking removes the participant's reach. Reports of a member or of a member's message never exist for a private 1:1, so this path can't reach a member's private conversation — the per-member isolation invariant holds. A **reply of Maurice's** can be reported anywhere (29 October 2026, App Review 1.2): the report keeps a copy of that reply and of the message before it, which the member is told before sending, and the operator reads only the copy, not the conversation or its title (`ai_reply_reports`, [[maurice-chat]]). The operator's queue is also in the app's Settings → Safety → *Open reports*, for admins.

## Push

When an event can't reach a live socket, it becomes an APNs push (`server/src/services/push.ts` + `apns.ts`, token-based ES256 over HTTP/2) — a room's activity, an invitation to a room, or a conversation Maurice opened ("Maurice: …", opening on the conversation when tapped). Device tokens carry a `platform` and a `household_tag`; the platform picks the APNs topic (`carnet-ios` → Carnet's bundle id `eu.chezmaurice.carnet.app` since the apps moved to the company team on 13 October 2026, `APNS_CARNET_TOPIC`; anything else → the Maurice app, `eu.chezmaurice.maurice`, `APNS_TOPIC`; a token is tried on both APNs environments, so a TestFlight build is reached from any server), so a conversation Maurice opens reaches Carnet too (19 September 2026, evening); dead tokens are pruned on Apple's say-so. Since 21 October 2026 the same events also reach a device that registered a Web Push subscription (the Android app, through UnifiedPush): the payload is encrypted to the device's keys and handed to its relay, which cannot read it ([[maurice-server]]). This is what notifies you across households when you're a guest elsewhere.

## The household archive

Since 19 September 2026 a household knows how to export itself. The **household archive** is a versioned `.maurice.tar.gz` (`maurice-archive` v1, `server/src/services/archive.ts`, format documented in `docs/household-archive.md`) holding everything the household *is*: `maurice.db` and the data-api databases as consistent `VACUUM INTO` snapshots checked by `integrity_check`, every member's notes with their git history, and `gardens.json`, images, files, uploads, avatars, `config.toml`, `secret.key` (the household key: it opens the mail stores' sealed subjects and readings, which a moved household would otherwise lose and pay for again — in the machine owner's archive only, see below), and a `manifest.json` (household, members, schema version, server version, contents). Left out: backups, logs, the dead Qdrant directory, the corpus vector index (regenerable), `.env` and the Mac's `ops/` secrets, and the bare git remotes under `~/.maurice/git`. **No password travels** (27 October 2026): the mail and address-book passwords and the members' Cloudflare tokens are emptied in the archive's copy of `maurice.db`, and each account arrives marked to be reconnected. A member's password is not the admin's to carry. The console's and the CLI's archive still holds the sessions and the provider keys, to move the household as it is: **it is a secret.**

The console's section 07, "Export this household" (`GET /admin/export`), streams it as `tar` reads, so the first byte leaves before the uploads are read. The console answers from the machine alone. `GET /api/admin/export` is gone (27 October 2026): an admin's session in the app was enough to carry every member's notes and conversations away, from anywhere. **A hosted household's admin** asks for it on their Chez Maurice account page, after giving their password again. The tower runs `bun run /app/scripts/export-household.ts --ttl 6h` in the container. The archive is written into the household's own volume (`household-exports/`, left out of the backups), and the household serves it **once** at `/export/<token>`: the token is 32 random bytes, kept only as its hash. The file is deleted when sent, or at expiry by an hourly sweep. The tower mails the link and never holds the archive (`services/householdExportLinks.ts`). That archive is the admin's profile (`withoutCredentials`): no session, API token in clear, pairing token, device code, PIN hash or provider key — and, since 28 October 2026, neither `secret.key` nor the mail stores it seals, so an admin cannot open the members' mail offline. After a move by that archive every member, the admin included, reconnects their mailbox and Maurice reads it again, at the household's cost. The console's archive keeps both: it is the machine owner's, made to move the household as it is. On a hosted household those keys are the operator's (the Scaleway key that trials share). In the new home each member joins again with a code. A fresh Maurice imports it into an empty data directory (refused if a `maurice.db` is already there; the server's own migrations bring the schema forward on first boot): `scripts/import-household.sh <archive> [dir]` on a Mac, `scripts/container.sh import <archive>` for a local container, `ops/household.sh add <host> <name> <domain> --from <archive>` for a household on a shared host — the archive travels over ssh's stdin and no copy stays on the host. Still by hand after an import: rebuilding the corpus index, and the `origin` remotes of the members' notes repositories, which point at the old machine.

## Ships vs. exists

All of this — members, roles, guests, rooms, device enrollment, PINs, foyer switching, push, the archive — is **core chat-engine functionality and ships**. None of it needs the experimental [[maurice-tools|tools]].

## Gaps & notes

- **The server is single-tenant.** There is one hardcoded `'default'` household per server; "multiple households" is a *client* capability (one device, many servers). The schema carries `household_id` everywhere, but a single server doesn't host multiple households. At home this is literal: each extra household is its own launchd agent, on its own port, with its own data directory and its own root for the members' notes (see [[maurice-architecture]]).
- **A device-pairing ceremony exists but is unused.** `/api/auth/pair` + the `devices` table (one-time pairing tokens) are implemented, yet the app pairs via the unauthenticated `/api/health` — the token flow is currently orphaned.
- **Sessions don't expire** in this version.
- **A self-hosted household's links open the browser first.** The apps can only declare `*.chezmaurice.eu`, so on any other name the invitation link shows the /join page, and its "Open" buttons hand over to the app.
- **No in-app place to rename a household or change its face.** The API is there (admin only) and the tower uses it once, at creation; after that it takes a direct API call or the database. A household made before the tower keeps its derived icon until someone sets one.
- **An admin's open invitation makes a standard member, never a guest**; a guest comes either from the console (any reach) or from a member's own invitation (reach: that member alone, widened only in the console). And `maurice://` links open only the iOS app: the macOS target generates its Info.plist and declares no URL scheme, so on a Mac the invitation link is pasted into the address field.
- **Guest persona access has no override** — it reuses each persona's `maurice_access` list rather than a guest-specific grant.
- **"Child" is a box, not a birth date** — the server knows nothing of ages; the admin ticks it, and only what Maurice does on his own reads it (opening a conversation, the night's proposals). It does not change a child's model access or content rules, which are their own settings.
